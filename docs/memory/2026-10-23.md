```go
package middleware

import (
    "net/http"
    "strings"
    "github.com/golang-jwt/jwt/v5"
)

func AuthMiddleware(secret string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            authHeader := r.Header.Get("Authorization")
            if !strings.HasPrefix(authHeader, "Bearer ") {
                w.Header().Set("Content-Type", "application/json")
                w.WriteHeader(http.StatusUnauthorized)
                w.Write([]byte(`{"error": "Token de autenticación no proporcionado"}`))
                return
            }
            tokenString := strings.TrimPrefix(authHeader, "Bearer ")
            token, err := jwt.Parse(tokenString, func(t *jwt.Token) (interface{}, error) {
                return []byte(secret), nil
            })
            if err != nil || !token.Valid {
                w.Header().Set("Content-Type", "application/json")
                w.WriteHeader(http.StatusUnauthorized)
                w.Write([]byte(`{"error": "Token de autenticación inválido"}`))
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

## 2026-10-23 — TASK-A-10: Cerrar puertos internos en producción (`docker-compose.prod.yml`)

**Tipo:** Seguridad / Arquitectura / Docker
**Estado:** ✅ Completada

### Qué se hizo
- Verificado que `docker-compose.prod.yml` **no publicaba puertos internos** para postgres, backend-users, backend-mp, ni backend-materiales.
- Verificado que `docker-compose.yml` (dev) mantiene sus puertos expuestos para desarrollo local (5001, 5002, 5003, 5432).
- Añadido servicio `backend-materiales` a `docker-compose.prod.yml`:
  - `build: ./backend-materiales-go`
  - Sin sección `ports:` (puerto 5003 NO expuesto al host)
  - `env_file: .env` + variables de entorno con `DB_HOST=postgres`, `DB_PASSWORD=${DB_PASSWORD}`, `JWT_SECRET=${JWT_SECRET}`
  - `depends_on: postgres` con `condition: service_healthy`
  - En red `sisgad5-network` (comunicación vía DNS de Docker)
- Añadido servicio `frontend` a `docker-compose.prod.yml`:
  - `build: ./frontend`
  - `ports: "5004:5004"` (único puerto frontend expuesto)
  - Variables `VITE_API_URL=${VITE_API_URL}`, `VITE_FRONT_URL=${VITE_FRONT_URL}`
  - `depends_on: api-gateway`
- **Corregida indentación** en `api-gateway.environment:` (5 espacios → 4 espacios) para YAML válido.
- **Añadida** `MATERIALES_SERVICE_URL=http://backend-materiales:5003` al `api-gateway` (gateway proxy a Materiales service).
- **Añadido** `backend-materiales` a `api-gateway.depends_on` (orden de arranque garantizado).

### Por qué se hizo de esa manera
- AGENTS.md sección 8 (SEC-02): "Materials con JWT (middleware añadido), puerto 5003 aún expuesto" es un hallazgo **crítico**. El JWT middleware fue añadido en TASK-A-09, pero el puerto 5003 estaba expuesto en producción hasta ahora.
- Principio de mínima exposición: en producción, solo el Gateway (5000, localhost-only) y el Frontend (5004) deben ser accesibles desde fuera. PostgreSQL, Users, MP, y Materials son servicios internos que deben comunicarse solo dentro de la red Docker.
- Docker Compose resuelve nombres de servicio a IPs dentro de `sisgad5-network`, por lo que `backend-materiales:5003`, `backend-users:5001`, `postgres`, etc. funcionan como DNS internos.
- El Frontend expone 5004 porque es el punto de entrada público (nginx/proxy inverso en producción). El Gateway expone solo `127.0.0.1:5000` (localhost), no accesible externamente directamente.

### Puertos resultantes en producción

| Servicio | Puerto | Exposición | Justificación |
|---|---|---|---|
| `postgres` | 5432 | ❌ No expuesto | Solo accesible desde la red interna Docker |
| `backend-users` | 5001 | ❌ No expuesto | Solo vía Gateway |
| `backend-mp` | 5002 | ❌ No expuesto | Solo vía Gateway |
| `backend-materiales` | 5003 | ❌ No expuesto | Solo vía Gateway |
| `api-gateway` | 5000 | ✅ `127.0.0.1:5000` | localhost-only (nginx proxy) |
| `frontend` | 5004 | ✅ `:5004` | Punto de entrada público |

### Dónde están los cambios
- `docker-compose.prod.yml` — Añadidos servicios `backend-materiales` y `frontend`; añadida `MATERIALES_SERVICE_URL` y `depends_on` en `api-gateway`; corregida indentación.

### Verificación
- ✅ Solo 2 puertos publicados en prod: `127.0.0.1:5000:5000` (Gateway) y `5004:5004` (Frontend).
- ✅ No hay `ports:` en `postgres`, `backend-users`, `backend-mp`, ni `backend-materiales`.
- ✅ Todos los servicios backend están en `sisgad5-network`.
- ✅ `api-gateway` resuelve `backend-materiales:5003` vía DNS de Docker.
- ✅ `docker-compose.yml` (dev) no fue modificado — mantiene puertos para desarrollo.
- ✅ `MATERIALES_SERVICE_URL=http://backend-materiales:5003` añadida al gateway.

### Qué hemos aprendido
- En producción, la regla de oro: **solo Gateway + Frontend exponen puertos**. Todos los servicios backend (Users, MP, Materials, Postgres) deben estar sin `ports:` en compose.
- Docker Compose usa DNS interno: `nombre-servicio:puerto` funciona automáticamente dentro de la red.
- El indentación YAML incorrecta (5 espacios en lugar de 4) puede pasar desapercibida visualmente pero es un error de parsing.
- Separar compose de dev/prod (`docker-compose.yml` vs `docker-compose.prod.yml`) permite tener puertos abiertos en dev pero cerrados en prod.

## ADR-004: Prediction Service en Python + FastAPI

**Decisión:** Crear `prediction-service/` como servicio aparte en Python 3.11+ + FastAPI.

**Justificación:**
- Ecosistema ML maduro en Python (scikit-learn, XGBoost, Prophet, TensorFlow).

- Nueva BD (`bd_predictions`).
- Servicios auxiliares: MLflow (model registry), Airflow (pipelines).
- 19 tareas nuevas en Fase D.

## ADR-006: Docs Bilingües ES/RU (Archivos Paralelos)
